# Data collection

[Back to the README](../README.md)

| Data | Source | Notes |
| --- | --- | --- |
| **Candles (OHLCV)** | REST | Spot (1s to 1d) and USD-M Futures (1m to 1d: Binance has no futures candles below a minute), any configured symbol. Resumes from the newest stored candle, repairs gaps automatically. |
| **Funding rates** | REST | Futures. Full history from a configured start date, polled hourly. |
| **Open interest** | REST | Futures, per period (5m to 1d). Binance only keeps ~30 days of history, so this must run continuously to build a long series. |
| **Long/short ratio, taker volume** | REST | Futures, per period (5m to 1d), like open interest: Binance keeps ~30 days, so they must run continuously. One admin flag (`CollectMarketStatistics`) turns on both for a series. |
| **Liquidations** | WebSocket | Futures. No history exists, so only what arrives while the worker runs is stored. Binance sends at most one liquidation per symbol per second, so this is a sample, not a complete record. |

Highlights of the collection path:

- **Idempotent, fast writes:** binary `COPY` into a temp table, then `INSERT ... ON CONFLICT DO NOTHING`, so re-fetching any range is always safe.
- **Rate-limit aware:** one shared weight limiter per market, so all collectors draw from the same Binance budget; exponential backoff on failures.
- **Self-healing data:** a daily `LAG()`-based gap detector refills missing candles, and a short repair looks at the newest ones every hour (below). Database errors are never mistaken for an empty table. Holes the exchange itself has no candles for (maintenance, no trades) stay open and are not retried in a loop; they are logged and listed by the `candle-gaps` check of `/health`: per series how many gaps, how many candles are missing and from when. That check is always healthy, because such a hole is a fact about the data, not a fault of the collector; it is there so the people using the data can see where the holes are. The run between the start date and the first candle is not a hole: a symbol listed later simply has no candles before its listing. The exchange is asked about it once, it is reported apart (`listed-later` in the same check) and the panel offers to move the start date to the first candle.
- **Boundary-aligned scheduling:** one loop per timeframe wakes just after each candle closes.
- **Non-blocking liquidation pipeline:** the WebSocket callback only enqueues into a bounded `Channel<T>`; a single writer drains it in batches.
- **The short repair, every hour:** the daily scan reads a whole table, so a candle that was missed (the live stream wrote the next one first, so the normal sync never goes back for it) would wait up to a day. Every hour each table also gets a look at its last 14 days only, through the primary key, so it costs the same for a table of years. A hole found there is asked of the exchange. The exchange is asked about the same hole until it has answered empty 3 times (kept in memory); after that the daily repair is the only one that looks at it, so a hole the exchange itself does not have is not asked about for ever. A request that failed is not an answer and does not count, and neither does one that brought candles (the hole is being filled). The short repair only fills (and writes down a hole that stays empty, see the next bullet): what `/health` and the panel say about the holes (and the "new gap" alert) stay the daily scan's. A time frame longer than an hour (4h, 1d) wakes up for it a minute after the full hour. The window, the period and the number of asks are the section `GapRepair` of the worker's `appsettings.json` (`RecentWindowDays` 14, `RecentPeriodMinutes` 60, `MaxAsksPerHole` 3; environment: `GapRepair__RecentWindowDays` and so on).
- **Confirmed gaps:** when the exchange has answered `MaxAsksPerHole` times about the very same hole (the hourly and the daily repair both count) and every answer was empty, the hole is written to `config.candle_confirmed_gaps` (table name, first and last missing `open_time`, when, how many answers), insert only, one row per hole. Only a request that went through is an answer: a failed one creates no row (and the daily scan no longer calls it "likely missing on exchange"). The count is kept in memory, so a restart starts counting again; the row of a hole that is already written is not written twice. If the database cannot take the row, that is logged and it is tried again at the next look; the repair goes on. The collector's role may add rows and read them, nothing else; the program that makes signals may read them. A row stays when the exchange later fills the hole, so a reader should look at the candles too.
- **Live candles over WebSocket:** closed klines are stored the moment they close (the callback enqueues, one writer batches). The REST loop still runs at every boundary as the watchdog, and a socket reconnect triggers an immediate REST sync plus gap repair. Live candles are only accepted for a table after its first REST sync, so they can never hide missing history.
- **Config-driven:** which candle series to collect (and whether they also collect open interest, funding rate and liquidations) is chosen in the admin panel and stored in the database, no code and no redeploy (see [Candle series](configuration.md#candle-series-chosen-in-the-database)).
